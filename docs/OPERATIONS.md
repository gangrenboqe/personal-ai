# 运维视角（怎么部署 / 怎么监控 / 怎么排查故障）

> 这份文档是写给"要把它跑起来、并在出问题时搞定它"的人看的。
> **写它不需要新增一行代码**——它记录的是这个服务真实的运行方式与真实踩过的坑。
> 读完你能回答三个问题：**它怎么跑起来的、我怎么知道它还活着、它挂了我先查什么。**

---

## 一、30 秒看懂

**Personal AI 是一个跑在你自己电脑上的小服务**：浏览器访问 `127.0.0.1:8787`，
你说话，它转给模型，把回答**一个字一个字**推回页面上，同时把整段对话存进一个本地文件。

它只有三个东西在跑：

| 角色 | 是什么 | 在哪 |
|---|---|---|
| **服务本体** | Python 写的网页服务 | `127.0.0.1:8787` |
| **存储** | SQLite 单文件数据库（对话、任务都存在这） | `data/personal_ai.db` |
| **AI 网关** | 本机转发程序，负责真正去调模型 | `127.0.0.1:20128` |

**依赖链**：浏览器 → 服务 → 网关 → 上游模型。
**任何一环断了，服务都会告诉你断在哪**——这是它设计时就定下的原则（来源透明）。

## 二、部署

### 方式一：双击（推荐）

双击 `启动个人AI.bat`。它按顺序做三件事：

1. 看 `8787` 端口是否已被占用 → 是就说明**已经在跑了**，直接帮你开浏览器
2. 看 `20128`（网关）是否在跑 → 不在就后台拉起来，并**每 3 秒检查一次**（最多约 135 秒）
3. 启动服务；连不上网关会**自动重试一次**，仍不行才降级到离线模式

🔎 **它每一步都写了日志**：`%LOCALAPPDATA%\personal_ai\launch.log`
（即 `C:\Users\Administrator\AppData\Local\personal_ai\launch.log`）。
**出问题先看这个文件的最后一行**——它停在哪一步，就是死在哪一步。

### 方式二：命令行

```bash
omniroute serve --no-open --daemon      # 网关（加 --daemon 立刻返回，后台跑）
python scripts/start_local.py           # 服务；会自动取本机网关 Key，密钥只在进程内存里
```

然后访问 <http://127.0.0.1:8787>。

### 方式三：离线（不调真实模型）

```bash
python -m personal_ai --serve
```

页面能看、接口能打，但回答来自本地示例，**会以 `[mock]` 开头明确标注**——不伪装。

### ⚠️ 两个部署上的硬约束

- **Windows 的 `.bat` 必须是 GBK 编码 + CRLF 换行**，不能存成 UTF-8，也不能加 `chcp 65001`。
  否则 cmd 会按错误字节解析，报"命令语法不正确"然后**窗口一闪就关**（实测踩过）。
- **演示前先随便问一句预热**。上游模型冷启动实测要 10~12 秒才出第一个字，
  热起来之后约 1.6 秒。服务启动时会后台自动预热一次（`--no-warmup` 可关）。

## 三、监控

### 1. 健康检查（最常用）

```bash
curl http://127.0.0.1:8787/api/health
```

返回里要看的三个字段：

| 字段 | 看到什么算正常 | 看到异常说明什么 |
|---|---|---|
| `provider` | `openai_compat` | 如果是 `mock` → **没接上真模型** |
| `model` | 具体模型名 | — |
| `api_key_set` | `true` | `false` → 网关 Key 没取到 |

> 这个接口**永远不返回密钥内容**，只返回"有没有"。这是安全设计，不是漏了字段。

### 2. 看历史（数据是不是真的存下来了）

```bash
python -c "import sqlite3;c=sqlite3.connect('data/personal_ai.db');print(c.execute('select count(*) from messages').fetchone())"
```

或者用 `sqlite3` 直接查 `messages` 表（字段含 `provider` / `model` / `chain` / `ok`）。

### 3. 看模型调用（第三方留痕）

网关自己会记每一次调用：**`~/.omniroute/call_logs/<日期>/`**。
里面有 HTTP 状态、耗时、输入输出 token 数。
**这是第三方软件的记录，不是我自己写的日志——所以它可以当证据用。**

### 4. 看代码有没有被改坏

- **单元测试 31 项**（纯函数，毫秒级，不起服务）：`python -m unittest discover -s tests`
- **冒烟测试 32 项**（起服务打接口）：`python scripts/smoke_test.py`
- **CI 自动跑**：push / PR 时在 Ubuntu + Windows × Python 3.11 / 3.13 上跑，共 4 个组合

## 四、排查故障（症状 → 原因 → 怎么办）

| 症状 | 最可能的原因 | 怎么办 |
|---|---|---|
| **双击后黑窗口几秒就没了** | 服务其实多半起来了，只是窗口没了 | 看 `launch.log` 最后一行；窗口若还在，它会停在"按任意键关闭" |
| **回答以 `[mock]` 开头** | 没接上真实模型 | `curl /api/health` 看 `provider`；确认网关在跑、Key 存在 |
| **第一句要等十几秒** | 上游冷启动 | 等预热完成；别反复重启网关（重启又要冷启动一次） |
| **提示"已经在运行了"** | 8787 端口被占 | 正常，直接用就行；要重启先结束旧进程 |
| **页面一直转圈不出字** | 早期版本 SSE 与 HTTP/1.0 冲突 | 已修：服务端显式关闭连接。再出现请贴 `launch.log` |
| **某个老会话里答非所问** | 旧会话里有一条假回答被当成上下文 | 已修：假回答/失败回答不进上下文（仍留在库里可查）。开新会话即可 |
| **数据库文件删不掉** | Windows 上 SQLite 连接是**惰性释放**的 | 关掉进程等几秒；判断删除成功只能靠复查文件是否还在 |
| **导出的 PDF 机器读不出字** | 被浏览器打平成图形了 | 必须用 Chrome 无头 `--print-to-pdf` 导出；交付前用体检工具验（另有独立仓库） |

## 五、备份与迁移

**整个系统的状态就一个文件**：`data/personal_ai.db`。
拷走它 = 拷走全部对话与任务；换机器放回去即可。

密钥**不落盘**：它只在进程内存里存在，取自本机网关（`~/.omniroute/storage.sqlite`，只读）。
所以备份数据库**不会泄露任何密钥**。

## 六、已知边界（运维时必须知道）

| 边界 | 说明 |
|---|---|
| **不做鉴权** | 前提是**只监听 `127.0.0.1`（本机）**。这两件事是绑定的，**一旦改成对外监听就必须补鉴权** |
| **不做并发** | SQLite 单机单人使用足够；多人同时写没做处理 |
| **只验证过 1 家供应商 1 个模型** | 架构支持替换，但实际只跑通过这一家 |
| **只测过 Windows 11 + Python 3.11 / 3.13** | Linux / macOS 未在真机验证（CI 上跑的是 ubuntu-latest） |
